# Unified Login for newly created Meta apps

This fork adapts the community implementation by [henacosta1](https://github.com/henacosta1/openreply/commit/6f7a02a2759bc052b3e2741fc5bf10c074242890), preserving the original commit and author. Background: upstream issues [#103](https://github.com/diwenne/openreply/issues/103) and [#104](https://github.com/diwenne/openreply/issues/104). This is custom integration work, not an upstream-supported release. Automated checks do not establish successful live delivery.

Set META_LOGIN_CONFIG_ID to enable Unified Login for the instance. INSTAGRAM_APP_ID and INSTAGRAM_APP_SECRET then contain the **Meta app** ID and secret from Basic settings. FACEBOOK_APP_SECRET is the same Meta app secret for webhook verification. Keep these on the server, outside Git. With META_LOGIN_CONFIG_ID unset, the original Instagram Login path is retained. Do not switch this instance setting with older direct-Meta tokens connected: transport selection is global, not per account. Zernio remains separate.

Create an Instagram-compatible configuration in Meta's Unified Login setup. Use a system-user token, selecting the no-scheduled-expiry option. Register the exact HTTPS callback: /api/instagram/callback. Keep only Instagram profile, messaging, comment, and optional insights permissions needed by OpenReply. Ads access and publishing are not required for comment-to-DM. Community reports indicate business_management may also be required to assign Instagram assets; inspect the Facebook Login for Business configuration editor, and verify the resulting grants during onboarding. Requesting permissions in a configuration does not bypass Meta's access-level or review requirements.

OAuth now uses the Facebook dialog with config_id, preserving the signed workspace state and authenticated owner/admin check. The server exchanges the code at graph.facebook.com, enumerates all granted Instagram account IDs (following cursor pages on a fixed trusted host), and stores encrypted tokens only in the requesting workspace. Existing accounts in other workspaces or on Zernio are not replaced. Media and profile requests address the selected account ID, not the system user represented by /me.

No-scheduled-expiry tokens use null in the existing nullable database field rather than a fabricated date. An explicit expires_in from the code exchange is retained. Instagram user-token refresh endpoints are not called in Unified mode. Expiring system-user configurations require reauthorization; automatic business-integration token renewal is not implemented. No-expiry tokens can still be revoked and are not a guarantee of permanent access.

Before migration, verify one secondary account: profile/media reads, signed comments and messages webhooks, a comment keyword from a separate tester, initial private reply, button follow-up, and incoming DM keyword. Inspect delivery logs and queue health. Do not migrate all accounts or disconnect existing tools before the pilot passes. Recheck conversation routing at the selected-account migration step.

This fork additionally follows assigned-account pagination, avoids arbitrary pagination URLs, preserves explicit token expiry, omits an unnecessary bulk admin script, and adds regressions for multi-account handling, workspace authorization, legacy transport, and token error redaction. Credential and production configuration files must never be committed.
